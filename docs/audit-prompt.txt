You are auditing a codebase file-by-file toward an immaculate result. I will provide you with one or more files to
examine. Report findings first; after I approve them, apply the fixes, verify, and commit. This is an audit-AND-fix
pass — not read-only.

## Workflow

- **Findings first, then fix.** Report findings before touching anything; make NO edits until I approve specific
  findings. After approval: apply, verify, and commit when I say.
- **Verify, don't guess.** Search the codebase as needed to confirm cross-file claims — consumers, dead code,
  duplication, import conventions — BEFORE finalizing a finding or making a change. Resolve "needs verification" by
  checking; only ask when the code genuinely can't answer it.
- **Fix as found; don't defer.** When a fix crosscuts other files — not-yet-audited, already-audited, or shared —
  make it now. Don't park work in TODOs/memos. The goal is that a later file is already clean when we reach it.
- **Verify before deleting.** For dead code TypeScript won't flag (object/map members, query keys, string-keyed
  config, barrel re-exports), grep all usages first; zero consumers = dead (caller-first). When deleting a file or
  barrel, grep EVERY import form — relative (`./x`, `../x`), aliased (`@app/x`), AND `export *` re-export chains; a
  partial-path grep misses re-exporters (e.g. an aggregate barrel that re-exports the one you're deleting).
- **A "DRY" swap can change behavior.** Replacing inline logic with a shared util/type may differ on edge cases —
  diff the two implementations and flag the behavior change; don't present it as behavior-neutral.
- **No tests = the diff is the gate.** When a refactor touches behavior-sensitive code with no test coverage,
  "tests pass" is vacuous — gate on a careful per-item diff trace + typecheck, and note the missing coverage in the
  finding.
- **Decide by convention, with data.** When choosing to keep/remove/standardize a pattern (barrels, accessors,
  naming), measure the dominant convention with grep counts instead of assuming. Keep what's the real import
  surface; remove what's vestigial.
- **Immaculate = no dead weight AND no un-consolidated duplication — be decisive.** Clean, behavior-neutral wins that
  clear the bar (≥2 identical callers with an existing precedent, a grep-proven dead export) are not "optional" — apply
  them; don't hand a clean call back as "your call." Reserve genuine consultation for real judgment: over-abstraction
  risk, a behavior/visual change, or a large multi-file refactor — present those and get explicit sign-off.
- **Be specific.** Exact line numbers and code, with confidence levels (high / medium / needs-verification).
- **Gate on green.** After changes, run typecheck + lint + tests and report results; don't claim done without them.

## What to look for

### 1. Comments & JSDoc

The project philosophy: comments explain **why** (business rationale, non-obvious decisions), not **what** (the code
already shows what it does). The best comment is a well-named function.

Scrutinize comments with the SAME rigor as code, on the first pass — a restatement comment is dead weight just like
dead code, and it's easy to skim past while auditing the logic. Don't wait for a second pass (or a reviewer) to catch it.

**File headers** — every file needs one BEFORE imports:
```typescript
/**
 * Plain English Title (not the class/component name)
 *
 * One-line description adding context beyond the filename.
 */
```
- Title should be plain English (e.g., "Audit Log Viewer"), NOT the component/class name (e.g., not "AuditLogViewer")
- No bullet lists or feature enumerations in the header
- Flag missing file headers

Comments that SHOULD exist — flag if missing:
- Business rationale (e.g., why a timeout is 15min, why a specific algorithm was chosen)
- Non-obvious edge cases that would confuse a future reader
- Workarounds with ticket references (e.g., // Temporary: string union until shared-schemas v2.0 - ticket #456)
- TODOs with dates and ticket numbers (e.g., // TODO(2025-01-15): Migrate to domain events - ticket #234)

Comments that should NOT exist — flag for removal:
- Comments that restate what the code does (e.g., // Increment counter above counter++)
- Restatement inline comments on config/options objects (e.g., // Disable window focus refetch next to
  refetchOnWindowFocus: false). The property name IS the documentation.
- Parenthetical restatements on section divider comments (e.g., // Admin (admin-only operations) — the parenthetical
  restates the label). Keep dividers bare.
- Section dividers that only restate the adjacent symbol (e.g. // TUBE EVENT HANDLERS above setupTubeEventHandlers) →
  remove. A divider with a strategy/why suffix (e.g. // … — patches cache directly instead of invalidation) earns
  its place → keep.
- Self-promotional language: "INDUSTRY STANDARD", "BEST PRACTICE", "Enterprise-grade", "A++++ QUALITY", "Type-safe"
- Redundant markers: checkmarks (✅), "NEW:", "FIXED:", "ARCHITECTURAL FIX:"
- Process references: "Phase 2", "Refactored from", "Added in January 2025", "migrated from", "expanded from"
- Decorative dividers: //=====, // ***, decorative headers
- Commented-out code with no explanation of why it's kept
- "Defaults to X" JSDoc/comment that restates a default already in the code (a `?? X` or `= X` in the body) — the code
  is the source of truth; drop the restatement.
- Value/coordinate restatements sitting next to the literal they describe (e.g. `// (Lucide: cx=12, cy=12, r=10)` above
  `cx="12" cy="12" r="10"`, or a file-header description that just restates the title) — drop.
- Visual "narration" that describes what CSS/JSX renders rather than why (e.g. `// lift the tint + border so it reacts`
  above the hover rule) — drop; keep only the non-obvious why (a `!important`-avoidance trick, an intentional `||`).

JSDoc rules:
- USE JSDoc for: Public API functions, complex return types, @throws declarations
- SKIP JSDoc for: Private helpers, simple getters, obvious handlers, functions where the TypeScript types already tell
  the full story
- BAD JSDoc restates the signature: /** @param data - The tube data @returns The tube */
- GOOD JSDoc adds behavioral context: /** Creates tube with position conflict validation. Emits 'tube_created' socket
  event. */
- Flag any JSDoc that just repeats parameter names/types without adding meaning
- Once a type/interface is UNEXPORTED (internal to its file), its per-field JSDoc bar rises sharply — the impl is right
  there, so document only genuinely non-obvious fields, not every one.
- Every `eslint-disable` / `eslint-disable-next-line` must carry a `-- reason`; flag bare ones. A `prefer-nullish-coalescing`
  disable sitting on code that already uses `??` is dead (the rule never fires) — remove it.

Self-documenting code check:
- If a comment exists only to compensate for a poor function/variable name, flag the naming as the real issue, not the
  missing comment

### 2. File Naming & Organization

Naming conventions:

┌─────────────┬───────────────────────────────┬─────────────────────────────────────────┐
│    Type     │          Convention           │                 Example                 │
├─────────────┼───────────────────────────────┼─────────────────────────────────────────┤
│ Components  │ PascalCase with domain prefix │ TubeEditorModal.tsx, AuthLoginModal.tsx │
├─────────────┼───────────────────────────────┼─────────────────────────────────────────┤
│ Hooks       │ camelCase with use prefix     │ useTubesQuery.ts                        │
├─────────────┼───────────────────────────────┼─────────────────────────────────────────┤
│ Services    │ PascalCase + Service          │ TubeService.ts                          │
├─────────────┼───────────────────────────────┼─────────────────────────────────────────┤
│ Stores      │ camelCase + Store             │ modalStore.ts                           │
├─────────────┼───────────────────────────────┼─────────────────────────────────────────┤
│ Type files  │ camelCase + Types             │ bulkUpdateTypes.ts                      │
├─────────────┼───────────────────────────────┼─────────────────────────────────────────┤
│ Directories │ kebab-case                    │ ui/components/                          │
├─────────────┼───────────────────────────────┼─────────────────────────────────────────┤
│ Constants   │ UPPER_CASE                    │ BOOTSTRAP_TIMEOUT                       │
└─────────────┴───────────────────────────────┴─────────────────────────────────────────┘

Component naming (entity-first): Domain prefix → entity → specifics → suffix.
Example: TubeLockNoteModal, AuthPasswordResetPage.
Established suffixes: Modal, Tab, Panel, Page, Form, Row, Button, Settings, Dashboard, Indicator, Field.

ui/components/ subdirectories: Feature-named, unprefixed (domain path provides context). Use feature names not UI
patterns — gateway/ not modals/, editor/ not forms/. Small shared presentational helpers can use a catch-all like
displays/.

Flag these issues:
- File name doesn't match what the file actually exports or does (e.g., a file named helpers.ts that only contains
  validation logic — should be validation.ts)
- File name uses the wrong casing convention for its type (e.g., a hook file in PascalCase, a component file in
  camelCase)
- Generic or vague file names that don't describe the contents (e.g., utils.ts, helpers.ts, misc.ts, index.ts that
  re-exports nothing meaningful)
- File appears to be in the wrong directory given what it does (e.g., a UI component sitting in a utils/ folder, a
  hook living in components/)
- File contains multiple unrelated concerns that should be split (e.g., a single file exporting both a React component
  and an API call helper)
- Inconsistency with sibling files in the same directory (e.g., all other files in the folder are PascalCase but one
  is camelCase)
- Directories named after UI patterns instead of features

Loose files:
- Flag files sitting directly in a directory when all sibling entries are subdirectories (except index.ts barrel files).
  Loose files should be moved into the most appropriate existing subdirectory or a new one if none fits.
- When recommending a move, check what already imports the file — the import path change is part of the finding.

### 3. Duplication

- Logic duplicated WITHIN the file (similar blocks, repeated patterns that could be consolidated)
- Logic duplicated ELSEWHERE — verify by searching, then consolidate to a shared home
- Magic strings/keys duplicated across files (localStorage keys, base URLs, query-key roots, event names) →
  centralize to a single owner

### 4. Technical Debt

- Overly complex logic that could be simplified
- Inconsistent patterns (e.g., mixing async styles, inconsistent error handling)
- Magic numbers/strings without explanation. (Numbers inside a named-key config object are self-documenting; flag
  standalone literals that recur or carry meaning.)
- Redundant type annotations the initializer already fixes (`x: boolean = false`, `x: number = 0`) → drop them; but
  KEEP load-bearing ones that widen on purpose (e.g. `Set<string>` so `.has(someString)` typechecks instead of a
  literal-union)
- Redundant parameters that are always passed the same module singleton (e.g. a queryClient param that's always the
  imported instance) → drop the param, use the import
- Thin handler wrappers that only forward to a store action or prop (`const handleX = () => clearX()`) → pass the
  action directly
- Single-use components/helpers extracted only to shrink a file — premature abstraction; extract on genuine reuse or
  to isolate a cohesive, separable concern (e.g. a modal stack), not the interdependent core of a large component
- Poor naming that obscures intent
- Awkward/redundant naming where the method name restates its parent (e.g., storage.storage(), tubes.lists() that
  returns the same key as tubes.list()). Flag with a suggested rename.
- Props passed through components when the child could call the hook directly (unnecessary prop drilling of hooks)
- Missing error handling at system boundaries
- Tight coupling that makes the code fragile

### 5. Dead/Zombie Code

- Exported functions/variables unused codebase-wide (verify by grepping all consumers, not just this file)
- Speculative exports/keys/fields/props with zero PRODUCTION consumers — a prop/export used only by a dev preview,
  mock, or test harness still counts as speculative (dead query keys, unused result fields, "for later" methods)
- Barrels are a two-part decision: DELETE a barrel with zero external importers (everyone deep-imports it, so it
  isn't the real surface); KEEP-and-TRIM a barrel that IS the surface (re-export only the externally-consumed
  symbols, drop the rest). Decide with grep counts — barrel-path imports vs deep-path imports. Don't go barrel-free;
  barrel headers may stay title-only. With a two-layer barrel (a folder `index.ts` PLUS an aggregate like `@shared/ui`),
  decide per symbol kind: COMPONENTS stay in the barrel (it's the component surface) even when some consumers deep-import
  them; TYPE re-exports trim to only those consumed via that barrel (a type consumed only via a deep path → drop the
  barrel re-export, keep it exported at source); HELPER FUNCTIONS don't belong in the barrel. A `*Props` interface used
  only in its own file with no external importer → unexport it (drop `export`).
- Unreachable or constant-by-guard code paths: branches hidden by earlier, broader checks (e.g., a 401/403 check
  after a general 4xx check that already covers it); a condition made always-true/false by an enclosing guard (e.g.
  `{(a || b) && …}` inside a branch already gated on `a || b`); an `else` unreachable because an upstream check returned
- Variables assigned but never read
- Imports that aren't used in the file
- Feature flags or conditional branches that appear permanently stale
- Completely unused or dead files — a whole component can be exported through its folder barrel AND re-exported through
  an aggregate barrel (e.g. `@shared/ui`) yet have zero real consumers, which makes it look alive. Confirm liveness by
  grepping the JSX render site (`<Name`) and every import site across the tree — not just "is it exported." (Several
  fully-built, barrel-re-exported components this pass turned out to have zero consumers.)

## After Changes

Commit only when I say. Commits are batched by top-level directory, in this exact format:
audit: <directory scope> — <specific changes, comma-separated>

Collateral cross-cutting changes from a dir's audit ride along in that dir's commit — don't split them out. No
co-author footer. Before committing: gate on green (typecheck + lint + tests), then stage precisely — exclude
unrelated work-in-progress from other sessions.

Examples:
- audit: hooks directory — move field resolver hooks to @domains/tubes/hooks, move useAuthSocketSync into lifecycle
  subdirectory
- audit: contexts directory — remove dead useResolvedTheme/useIsDarkMode exports, restatement JSDoc/comments, simplify
  BootstrapContextValue to type alias
- audit: bootstrap directory — consolidate step labels, fix dead types, extract offline handler

The directory scope stays consistent across related commits. Each commit message describes the specific changes made
in that pass.
